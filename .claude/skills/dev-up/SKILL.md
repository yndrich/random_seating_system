# 개발 스택 기동 + 스모크 (dev-up)

이 프로젝트의 가장 흔한 함정: **백엔드(8000)가 안 떠 있으면 Vite 프록시가 `/api/*`에
500(`net::ERR_ABORTED`)을 반환한다 — 프론트 버그가 아니다.** dev에서는 두 서버를 함께
띄워야 한다(`vite.config.ts`가 `/api`를 `127.0.0.1:8000`으로 프록시). 자세한 배경은
루트 `CLAUDE.md`의 "교차 관심사" 참고.

## 1. 백엔드 먼저 (port 8000)

백엔드를 **백그라운드로** 띄운다(Bash의 `run_in_background` 사용). 루트 `.venv`의
인터프리터를 직접 호출한다(activate 불필요):

```bash
cd backend && ../.venv/bin/python -m uvicorn app.main:app --reload --port 8000
```

> 의존성이 아직 없으면 먼저: `.venv/bin/python -m pip install -r backend/requirements.txt`
> (루트에서). `.venv`가 없으면 `python -m venv .venv`로 만든 뒤 설치.

## 2. health로 기동 확인

서버가 받을 준비가 됐는지 health로 확인한다(이 엔드포인트는 세션 헤더가 필요 없다):

```bash
curl -s http://127.0.0.1:8000/api/health    # {"status":"ok"} 기대
```

`ok`가 나올 때까지 기다린 뒤 다음 단계로 간다. 연결 거부면 아직 부팅 중이거나 8000
포트가 이미 점유된 상태다.

## 3. 프론트엔드 (port 5173)

별도 백그라운드 프로세스로 띄운다:

```bash
cd frontend && npm run dev      # 최초 1회는 npm install 먼저
```

→ http://localhost:5173 에서 앱 접속. `/api/*`는 자동으로 8000으로 프록시된다.

## 4. API 스모크 테스트 (백엔드만으로 검증)

프론트 없이도 백엔드 계약을 한 바퀴 돌려본다. 번들된 스크립트가 세션 생성 → 참가자 bulk
추가 → preview → commit → met_count 증가까지 실제 HTTP로 검증한다(stdlib만 사용, 추가
설치 불필요):

```bash
.venv/bin/python .claude/skills/dev-up/scripts/smoke_api.py
# 옵션: --base http://127.0.0.1:8000  -n 12(참가자 수)  --tables 3
```

각 단계가 `✓`로 통과하고 마지막에 `✅ 스모크 통과`가 나오면 백엔드가 정상이다. 어느
단계에서 멈추면 그 지점이 깨진 곳이다(예: "연결 실패"면 8000이 안 떠 있는 것).

이 스모크는 **변경 후 회귀 확인**에도 유용하다. API/스키마/알고리즘을 건드린 뒤
`pytest`(단위) + 이 스모크(통합 HTTP) + `npm run build`(프론트 타입)를 함께 돌리면
3계층이 다 맞는지 빠르게 확인된다.

## 5. 정리

작업이 끝나면 두 백그라운드 프로세스를 종료한다(해당 Bash task를 kill). 세션 상태는
인메모리라 백엔드 프로세스를 끄면 모두 휘발된다 — 별도 정리 불필요.

## 참고 — 포트/프로세스 트러블슈팅

- **5173에서 500/ERR_ABORTED**: 거의 항상 8000이 안 떠 있다. 2단계 health로 확인.
- **8000 기동 실패(Address already in use)**: 기존 uvicorn이 살아있다. 해당 프로세스를
  찾아 종료하거나 다른 포트로 띄운다(단, 프록시 타깃이 8000 고정이므로 8000 권장).
- **세션 404가 반복**: 백엔드를 재시작하면 인메모리 세션이 날아간다. 프론트는
  `client.ts`가 404 시 세션을 1회 재생성·재시도하지만, 직접 API를 호출하는 스크립트는
  새 세션을 만들어야 한다(스모크 스크립트는 매번 새로 만든다).
